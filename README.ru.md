# Pulse — собственный RSS-ридер

**Языки:** [English](README.md) · [Deutsch](README.de.md) · [Русский](README.ru.md)

Pulse — многопользовательское веб-приложение для чтения RSS и Atom. Оно работает локально на React и TypeScript, API на Go/Chi, PostgreSQL и Nginx. Фронтенд, бэкенд и база данных запускаются отдельными файлами Docker Compose.

## Требования

- Docker Engine с плагином `docker compose`
- Исходящий HTTP/HTTPS-доступ сервера к публичным RSS-адресам

Устанавливать Go и Node.js на хосте не нужно: инструменты сборки находятся в контейнерах. Версии закреплены в манифестах и lock-файлах.

## Локальный запуск

Все команды выполняются из корня проекта. Создайте локальные настройки и общую Docker-сеть один раз:

```sh
cp .env.example .env
docker network create rss-reader-net
```

До первого запуска API с пустой базой укажите в `.env` `INITIAL_ADMIN_EMAIL` и уникальный `INITIAL_ADMIN_PASSWORD` длиной не менее 12 символов. Они используются только для создания первого администратора. Для локального HTTP оставьте `SESSION_COOKIE_SECURE=false`.

Запускайте базу, API и веб-сервер именно в таком порядке:

```sh
docker compose -f compose.database.yml up -d
docker compose -f compose.backend.yml up -d --build
docker compose -f compose.frontend.yml up -d --build
```

Откройте <http://localhost:8090>. Если порт занят, измените `WEB_PORT` в `.env`. Для доступа из локальной сети задайте `WEB_BIND=0.0.0.0`. Если на хосте уже работает Nginx, оставьте `WEB_BIND=127.0.0.1` и настройте прокси на `http://127.0.0.1:8090`.

Исходники фронтенда подключены к контейнеру. В режиме разработки контейнер проверяет TypeScript и запускает Vite в watch-mode. При изменении исходников `frontend/dist/` пересобирается автоматически, а Nginx отдаёт обновлённую сборку. Чтобы увидеть изменения, обновите страницу в браузере. Пересобирать вручную после правок исходников не нужно. Пересоздайте контейнер после изменения зависимостей или Docker-образа:

```sh
docker compose -f compose.frontend.yml up -d --build
```

Исходники бэкенда подключены к API-контейнеру. После изменений Go перезапустите API:

```sh
docker compose -f compose.backend.yml restart api
```

## Тесты фронтенда

Запускайте компонентные и браузерные тесты Playwright во фронтенд-контейнере:

```sh
docker compose -f compose.frontend.yml exec frontend npm run lint
docker compose -f compose.frontend.yml exec frontend npm run test -- --run
docker compose -f compose.frontend.yml exec frontend npm run test:e2e
```

Playwright запускает локальный Vite-сервер и использует детерминированные API-фикстуры. Эталонные снимки хранятся в `frontend/test/e2e/`. После намеренного изменения интерфейса просмотрите снимки и обновите их командой:

```sh
docker compose -f compose.frontend.yml exec frontend npm run test:e2e:update
```

Файлы Compose используют внешнюю сеть `rss-reader-net`, поэтому группы сервисов можно запускать и останавливать отдельно. PostgreSQL должна запуститься до API; при старте API ожидает готовность базы.

## Языки интерфейса

Интерфейс доступен на английском, немецком и русском языках. При первом посещении используется английский. Выберите язык в панели инструментов или на экране входа; выбор сохраняется в локальном хранилище браузера. JSON-файлы переводов расположены в `frontend/src/locales/`.

Чтобы добавить язык, создайте JSON-файл на основе ключей `en.json`, добавьте код языка в `supportedLanguages` и `resources` файла `frontend/src/i18n.ts`, а его самоназвание — в `frontend/src/LanguageSelector.tsx`. Английский каталог является исходным и резервным.

## Скилы для AI-агентов

Проектные скилы хранятся в `.agents/skills/`. Этот каталог указан в `.gitignore`, поэтому скилы не входят в репозиторий, и в свежем клоне их нет. В `skills-lock.json` записаны скилы, которые поддерживаются во внешних источниках, вместе с их upstream-источниками; скрипт проекта восстанавливает или обновляет их с помощью Node.js 24:

```sh
bash scripts/sync-skills.sh install  # восстановить скилы из lock-файла при необходимости
bash scripts/sync-skills.sh update   # обновить скилы, отслеживаемые через lock
```

После восстановления или обновления скрипт добавляет специальные правила Pulse обратно в проектный скил `handoff`. Скилы, которых нет в `skills-lock.json`, например рабочие скилы Superpowers (`obra/superpowers-skills`) и `diagnosing-superpowers`, скрипт не восстанавливает; при необходимости скопируйте их в `.agents/skills/` самостоятельно. Не устанавливайте проектные скилы глобально.

## Production-сборка и развёртывание

Для production используется `compose.production.yml`. Он собирает release-образы без монтирования исходников. Создайте файл настроек и замените все значения `CHANGE_ME`:

```sh
cp .env.production.example .env.production
```

Укажите начальные данные администратора. Используйте HTTPS через TLS reverse proxy, оставьте `SESSION_COOKIE_SECURE=true` и не публикуйте внутренний HTTP-порт в недоверенную сеть. По умолчанию веб-сервис доступен только на `127.0.0.1:8090`.

Проверьте конфигурацию, соберите образы и запустите сервисы:

```sh
docker compose --env-file .env.production -f compose.production.yml config -q
docker compose --env-file .env.production -f compose.production.yml build --pull
docker compose --env-file .env.production -f compose.production.yml up -d
docker compose --env-file .env.production -f compose.production.yml ps
```

API применяет миграции при запуске. После создания администратора удалите `INITIAL_ADMIN_EMAIL` и `INITIAL_ADMIN_PASSWORD` из `.env.production` и пересоздайте API-контейнер:

```sh
docker compose --env-file .env.production -f compose.production.yml up -d --force-recreate api
```

Перед обновлением production сделайте резервную копию базы, затем пересоберите и запустите образы командами выше. Также доступен скрипт:

```sh
./scripts/update-production.sh
```

Он требует чистую копию репозитория на ветке `master`, создаёт резервную копию базы скриптом `scripts/backup-production.sh` (см. [Резервные копии production](#резервные-копии-production); если копия не удалась, обновление прерывается), выполняет fast-forward из `origin/master`, проверяет конфигурацию Compose, пересобирает сервисы и ждёт health checks. Не подключайте локальный Compose базы к каталогу production-данных.

Поиск по статьям использует расширение PostgreSQL `pg_trgm`, которое создаёт миграция `016_article_search.sql`. Оно входит в официальные образы PostgreSQL и является доверенным (trusted), поэтому владелец базы может создать его без прав суперпользователя; при другой установке PostgreSQL убедитесь, что расширения contrib установлены. Миграция один раз перезаписывает каждую сохранённую статью и строит поисковый индекс; в тесте для 500 000 статей это заняло около 3 минут. API начинает принимать соединения только после этого. Поэтому health check продакшен-API допускает стартовый период 15 минут, а скрипт обновления ждёт health checks до 900 секунд (можно изменить: `DEPLOY_WAIT_TIMEOUT=<секунды> scripts/update-production.sh`). Если и этого не хватит, следите за `docker compose --env-file .env.production -f compose.production.yml logs -f api`, пока API не сообщит, что слушает порт.

## Данные, пользователи и обновление лент

Первый Administrator получает существующую общую библиотеку при миграции. Администратор может создавать пользователей с ролями `Administrator` или `Reader`; публичной регистрации нет. У каждого пользователя собственные папки, подписки, статусы чтения и сохранённые статьи. Нормализованные адреса фидов и их статьи общие, а состояние чтения остаётся личным. Администратор не может просматривать библиотеки других пользователей.

Каждый пользователь может подписаться максимум на 100 лент. API проверяет лимит до загрузки нового источника и повторно — при сохранении подписки, в том числе при параллельных запросах.

TTL общих фидов по умолчанию равен 15 минутам; допустимо от 5 до 1440 минут. Фоновый планировщик запускается примерно через 10 секунд после старта API и затем каждую минуту проверяет, какие фиды пора обновить. Общий фид обновляется с наименьшим интервалом среди его подписчиков (личный интервал, иначе общий интервал планировщика из панели администрирования), но не чаще TTL общих фидов; фид с ошибкой запрашивается повторно через тот же интервал. Фиды запрашиваются условно (`ETag`/`Last-Modified`), поэтому неизменённые фиды не скачиваются повторно. API обновляет уникальные фиды параллельно ограниченным пулом Go-воркеров. Параметр `RSS_REFRESH_CONCURRENCY` в `.env` задаёт от 1 до 32 параллельных обновлений (по умолчанию 4). Блокировки базы и TTL предотвращают повторный запрос во время обновления и до окончания TTL. API держит не более `DB_MAX_CONNS` соединений с PostgreSQL (по умолчанию 12, допустимо от 2 до 100; значение должно быть меньше `max_connections` сервера, по умолчанию 100); при недопустимом значении API не запускается.

Разрешены только публичные HTTP/HTTPS RSS- и Atom-адреса. Loopback-, приватные и локальные сетевые адреса блокируются. Pulse хранит метаданные и краткие описания; полный текст статьи остаётся на сайте источника.

Перед сохранением Pulse проверяет заголовок и описание каждой новости по редактируемому администратором словарю запрещённых слов. Регистр не учитывается; совпадения ищутся по целым словам и фразам, в том числе через пунктуацию. Новости с совпадениями сохраняются в карантине вместе с заголовком, ссылкой, описанием и исходной датой публикации; остальные новости того же фида поступают в библиотеку. Начальный словарь на русском, английском и немецком включает термины спама, мошенничества, эротики и порнографии. Администратор может добавлять и удалять слова. Удаление слова само по себе не восстанавливает новости из карантина.

В панели администратора отображается до 100 записей карантина, сначала ожидающие решения. Для каждой записи доступны новость и описание, фид, совпавшее слово, аккаунт, который первым добавил фид, исходная дата публикации, время последней блокировки и статус. Администратор может разрешить или отклонить новость. Отклонение обратимо: позднее новость можно разрешить. Разрешённая новость поступает в общую таблицу статей с исходной датой публикации, а не датой решения, и появляется только в библиотеках пользователей, подписанных на этот источник. Библиотека администратора подчиняется тому же правилу.

Повторные обновления фида обновляют содержимое карантина без дубликатов и сохраняют ранее принятое решение. Разрешённые записи остаются историей без кнопок модерации; повторное совпадение со словарём не блокирует их снова. Вместе с решением сохраняются администратор и время решения. Старые записи журнала без сохранённых описания и даты публикации доступны только для просмотра; действия модерации для них недоступны.

Для сессий используется случайная HttpOnly-cookie с `SameSite=Strict`, срок действия — 14 дней. Пароли хранятся как Argon2id-хэши. Вне локальной loopback-разработки включите HTTPS и `SESSION_COOKIE_SECURE=true`.

Вход ограничен по частоте: после 10 неудачных попыток для аккаунта за 15 минут или 30 попыток с одного клиентского адреса за минуту API отвечает `429`, пока окно не позволит новые попытки. Счётчики хранятся в PostgreSQL, поэтому сохраняются после перезапуска и действуют для всех экземпляров API; если их не удаётся прочитать, вход завершается ошибкой, а не пропускает проверку. API берёт адрес клиента из `X-Real-IP` только для запросов из сетей, перечисленных в `TRUSTED_PROXY_CIDRS` (CIDR через запятую; пустое значение означает loopback, RFC 1918 и `fc00::/7`, включая Docker-сеть встроенного Nginx; `none` отключает использование заголовка). При недопустимом значении API не запускается. У каждого пользователя может быть не более 10 заявок на ленты, ожидающих одобрения.

Встроенный Nginx отправляет Content Security Policy и другие заголовки безопасности браузера. Он не завершает TLS и поэтому не отправляет `Strict-Transport-Security`; настройте HSTS на reverse proxy, который завершает TLS (например, `add_header Strict-Transport-Security "max-age=31536000" always;` в Nginx на хосте).

### Хранение данных

Фоновая задача обслуживания запускается примерно через минуту после старта API и затем каждые 6 часов. Она удаляет статьи, у которых и дата публикации, и время первого получения старше `ARTICLE_RETENTION_DAYS` (по умолчанию 180, допустимо 30–3650), если ни один пользователь не сохранил их; состояния прочтения и сохранения удаляются вместе со статьями. Обновление фида не добавляет повторно датированные записи старше этого срока, если их ещё нет в базе. Записи карантина с решением (разрешено/отклонено) и немодерируемые старые записи удаляются, когда и решение, и их последнее появление при обновлении старше `QUARANTINE_RETENTION_DAYS` (по умолчанию 90, допустимо 7–3650); ожидающие записи сохраняются. Та же задача удаляет истёкшие сессии. Значение `0` отключает соответствующую очистку; при недопустимом значении API не запускается.

## Резервные копии, журналы и остановка

### Дамп локальной базы

Перед переносом или обновлением сделайте дамп локальной базы разработки:

```sh
docker compose -f compose.database.yml exec -T db pg_dump -U pulse pulse > pulse-backup.sql
```

Если в `.env` заданы другие `POSTGRES_USER` или `POSTGRES_DB`, используйте их.

### Резервные копии production

`scripts/backup-production.sh` записывает сжатый архив `pg_dump` (формат custom) production-базы в `backups/production/pulse-<время UTC>.dump`. Каталог получает права 700, каждая копия — 600. Дамп сначала пишется во временный файл и переименовывается, только если он не пуст и `pg_restore --list` может его прочитать. Затем скрипт удаляет копии старше `BACKUP_KEEP_DAYS` дней (по умолчанию 14), включая обычные `.sql`-дампы старых версий скрипта обновления, но никогда не удаляет самую новую копию. Сервис `db` должен быть запущен. Ход работы выводится в stderr, путь к новой копии — в stdout.

```sh
./scripts/backup-production.sh
BACKUP_KEEP_DAYS=30 ./scripts/backup-production.sh
```

Копии хранятся на том же хосте, что и база. Регулярно копируйте `backups/production/` на другую машину или в другое хранилище.

Для ежедневной копии через cron добавьте такую строку в crontab пользователя, которому разрешено запускать `docker` (замените `/srv/pulse` на путь к рабочей копии):

```cron
17 3 * * * cd /srv/pulse && ./scripts/backup-production.sh >> /var/log/pulse-backup.log 2>&1
```

Или используйте таймер systemd. `/etc/systemd/system/pulse-backup.service`:

```ini
[Unit]
Description=Pulse production database backup
Requires=docker.service
After=docker.service

[Service]
Type=oneshot
WorkingDirectory=/srv/pulse
Environment=BACKUP_KEEP_DAYS=14
ExecStart=/srv/pulse/scripts/backup-production.sh
```

`/etc/systemd/system/pulse-backup.timer`:

```ini
[Unit]
Description=Daily Pulse production database backup

[Timer]
OnCalendar=*-*-* 03:17:00
RandomizedDelaySec=15min
Persistent=true

[Install]
WantedBy=timers.target
```

Включите его командой `sudo systemctl daemon-reload && sudo systemctl enable --now pulse-backup.timer` и проверяйте через `systemctl list-timers pulse-backup.timer` и `journalctl -u pulse-backup.service`. Сервис работает от root, если не добавить `User=` с учётной записью из группы `docker`.

### Восстановление production

```sh
./scripts/restore-production.sh --yes backups/production/pulse-20261101T031700Z.dump
```

Без `--yes` скрипт только объясняет, что будет заменено. С `--yes` он проверяет, что архив читается, сохраняет текущую базу через `backup-production.sh` (`--skip-safety-backup` пропускает этот шаг, если текущую базу невозможно выгрузить), останавливает `api` и `web`, удаляет и заново создаёт базу, восстанавливает архив через `pg_restore`, запускает все сервисы и ждёт их health checks до `DEPLOY_WAIT_TIMEOUT` секунд (по умолчанию 900). Всё, что было записано после создания копии, теряется, включая более новые сессии, поэтому пользователям, возможно, придётся войти заново.

Обычные SQL-дампы (`*.sql` старых версий скрипта обновления) скрипт не восстанавливает. Остановите `api` и `web`, пересоздайте базу в контейнере `db` (`dropdb --force` и `createdb` от имени `POSTGRES_USER`), загрузите файл командой `psql -v ON_ERROR_STOP=1 -U <пользователь> -d <база> < <файл>.sql` через `docker compose ... exec -T db` и снова запустите сервисы.

**Откат обновления.** Миграции выполняются только вперёд; down-скриптов нет. Чтобы вернуться к предыдущей версии, сначала соберите образы предыдущего коммита, а затем восстановите копию, которую `update-production.sh` создал перед обновлением. Так старый API никогда не запустится на более новой схеме:

```sh
git checkout <предыдущий-коммит>
docker compose --env-file .env.production -f compose.production.yml build
./scripts/restore-production.sh --yes backups/production/<копия-перед-обновлением>.dump
```

Перед следующим запуском `update-production.sh` вернитесь на `master` (`git checkout master`).

### Проверка восстановления

Регулярно проверяйте восстановление, например раз в три месяца и после изменений в настройке копий, на одноразовой копии, а не на production-проекте. Проверка 2026-11-01 прошла так:

1. Скопировать `compose.production.yml` в пустой каталог и заменить `name:` на неиспользуемое имя проекта (`pulse-s9-prod`). Скопировать `scripts/backup-production.sh` и `scripts/restore-production.sh` в подкаталог `scripts/`, создать символические ссылки `backend` и `frontend` на рабочую копию и файл `.env.production` с тестовым паролем, тестовым администратором и свободным `WEB_PORT`. Относительный том `./data/postgres-production` тогда указывает внутрь копии, и настоящий каталог данных не затрагивается.
2. `docker compose --env-file .env.production -f compose.production.yml up -d --build --wait`, войти через веб-порт и создать папку «Before backup».
3. `scripts/backup-production.sh` создал архив размером 42 КБ с правами 600 в каталоге с правами 700.
4. Создать папку «After backup». `scripts/restore-production.sh <архив>` без `--yes` отказался работать; с `--yes` он сделал страховочную копию, остановил `api` и `web`, пересоздал и восстановил базу, и все три сервиса снова стали healthy.
5. После повторного входа список папок содержал «Before backup» и не содержал «After backup»: база вернулась к состоянию копии. Проверена и ротация: при `BACKUP_KEEP_DAYS=14` копии со временем изменения 20 дней назад были удалены, а самая новая копия сохранилась даже со старым временем изменения.
6. Очистка: `docker compose --env-file .env.production -f compose.production.yml down -v --rmi local` и удаление копии.

### Журналы и health checks

API пишет структурированные журналы (Go `log/slog`) в stderr. `LOG_FORMAT` выбирает `text` (по умолчанию, используется в локальных Compose-файлах) или `json` (по умолчанию в `compose.production.yml`); `LOG_LEVEL` — `debug`, `info` (по умолчанию), `warn` или `error`. Недопустимое значение останавливает API при запуске. Каждый запрос даёт одну запись `http request` с полями `method`, `path` (без строки запроса, в которой могут быть поисковые слова), `status`, `bytes`, `duration_ms`, `request_id` и `user_id` для вошедших пользователей; health checks пишутся только на уровне `debug`. Каждый ответ содержит заголовок `X-Request-ID` с тем же ID: корректный входящий `X-Request-ID` (до 64 символов из букв, цифр, `.`, `_`, `:` и `-`) сохраняется, всё остальное заменяется сгенерированным ID. Указывайте его, сообщая о проблеме. Планировщик обновлений пишет по одной записи `rss refresh cycle finished` на цикл или ручное обновление с числом источников (`targets`) и количеством `refreshed`, `not_modified`, `failed` и `skipped`; циклы без источников к обновлению пишутся только на уровне `debug`.

Журналы смотрите командой `docker compose -f <compose-файл> logs -f api`. Для JSON-журналов, например, `docker compose --env-file .env.production -f compose.production.yml logs --no-log-prefix api | jq 'select(.status >= 500)'` показывает неудачные запросы.

`GET /api/health/live` сообщает, что процесс API работает, не обращаясь к базе. `GET /api/health/ready` дополнительно проверяет базу (тайм-аут 2 секунды) и отвечает `503`, если она недоступна; health checks в Compose используют этот адрес. `GET /api/health` остаётся псевдонимом проверки готовности. Метрики Prometheus API пока не экспортирует.

### Остановка

Остановка локальных сервисов:

```sh
docker compose -f compose.frontend.yml down
docker compose -f compose.backend.yml down
docker compose -f compose.database.yml down
```

Данные PostgreSQL остаются в `data/postgres/`. Не удаляйте этот каталог, если хотите сохранить аккаунты и подписки.

## Структура проекта

- `frontend/` — React/TypeScript-приложение, конфигурация Nginx и контейнер.
- `backend/` — Go API, RSS/Atom-парсер и миграции PostgreSQL.
- `frontend/test/` и `backend/test/` — тесты, сгруппированные по компонентам.
- `data/postgres/` — локально подключённые данные PostgreSQL.
- `compose.frontend.yml`, `compose.backend.yml`, `compose.database.yml` — независимые локальные группы сервисов.
- `compose.production.yml` — production-сборка и развёртывание.
- `scripts/` — скрипты обновления, резервного копирования и восстановления production, а также синхронизации скилов агентов.
- `backend/openapi/openapi.json` — описание HTTP API в формате OpenAPI 3.1.
